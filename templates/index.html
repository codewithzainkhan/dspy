DSPy Live Lab

Watch a prompt get compiled — and optimized — in real time

Every click below makes a real call to your LM. Nothing here is pre-recorded. Work through the four steps in order the first time; after that, jump around freely.

🔑 key: not set 📄 data: not loaded ⚙️ optimized: no
1

Connect your API key

This app talks to an LM the same way common.py does in the rest of this project: dspy.LM(model, cache=True) then dspy.configure(lm=lm). Your key stays on your own machine — it's used to call OpenAI and nowhere else, and is never written to disk.

"Connect" makes one tiny real call to confirm the key and model work — the same check 00_check.py does.

2

Load a dataset

A dataset here is just labeled examples: a piece of text, plus the two labels DSPy should learn to predict. Use the built-in ticket-triage set, or bring your own — any label names work, DSPy learns whatever categories your data actually contains.

36 real support tickets, labeled by a rubric that's never written into any prompt — the point of the whole demo. See common.py in this project for the full list.

Format: CSV with header ticket,category,urgency, or JSON — an array of {"ticket": "...", "category": "...", "urgency": "..."} objects. ticket is the free text; category and urgency can be any labels you want (they don't have to match the built-in ones). Include at least 6–8 rows so there's enough to split into train/dev.

3

See the prompt. Then run it for real.

DSPy calls your typed input/output spec a Signature. It is not a prompt — it's a contract (field names, types, one instruction string). A function called ChatAdapter.format() turns that contract into the actual messages sent to the LM: a system message built from three parts (the field description, a strict wire format using [[ ## field ## ]] markers, and your instructions), then the input. Type anything below and click Preview prompt to see that function's real output — for free, no API call. Click Classify to actually send it and see the real answer.

Search for the best prompt

        

          "Best" is not a feeling — it's whatever your rubric (a scoring function) says. Pick what
          counts as correct below, pick a search budget, and DSPy will try candidate instructions and few-shot example
          sets, scoring each one against your dev set with that rubric, and keep whichever combination scores highest.
          Change the rubric and re-run, and it optimizes for a different definition of "best" — the rubric is
          a parameter you choose, not something built into DSPy.
